This training takes each one in turn — what it is, what it looks like done right, and how to verify it. Automation

The ada-wcag plugin

ada-wcag is a Claude Code plugin that applies these 15 checkpoints automatically when Claude writes web code. Once it's installed, every page, form, and component Claude builds starts from these standards rather than having them added afterward.

What it does

  • As you buildThe plugin guides the code Claude writes so it meets the 15 checkpoints from the start — semantic HTML, labels, contrast, focus indicators, and the rest, by default.
  • For a quick checkAsk Claude something like "check this header for accessibility" and it reviews just that piece, inline, without running the full audit.
  • Before launchType "run accessibility audit" and Claude walks you through every issue, sorted by severity, one fix at a time.

Beyond the 15 checkpoints

The 15 checkpoints are the core of an EUSD audit, but the plugin applies the complete WCAG 2.2 AA standard, so it also covers items that aren't on the list above. The most common of these:

  • Target sizeButtons, links, and controls must be at least 24×24 pixels — 44×44 for parent- and mobile-facing pages — so they're easy to tap (WCAG 2.5.8).
  • Dragging alternativesAnything you reorder or move by dragging must also work by click or keyboard (WCAG 2.5.7).
  • Focus never hiddenA sticky header, cookie banner, or fixed footer must not cover the element you've tabbed to (WCAG 2.4.11).
  • Consistent naming & orderThe same control is labeled the same way on every page, and navigation stays in the same order from page to page (WCAG 3.2.4, 3.2.3).
  • Help in a predictable placeContact and help links sit in a consistent spot across the site (WCAG 3.2.6).
  • More than one way to find thingsMulti-page sites offer at least two ways to locate content — menu, search, sitemap, or breadcrumbs (WCAG 2.4.5).
  • Helpful error messagesWhen a form rejects input, the message says how to fix it, not just that it's wrong (WCAG 3.3.3).
  • Guarding consequential actionsSubmissions with real consequences — payments, legal commitments, deletions — get a confirmation step or an undo (WCAG 3.3.4).

How to install it

These are slash commands you type at the Claude prompt — start Claude Code in your project first (run claude in your terminal), then enter them inside that session, not in your regular command line. Once per machine you use Claude Code on:

/plugin marketplace add Escondido-Union-School-District/eusd-ada-toolkit
/plugin install ada-wcag@eusd-ada-toolkit

How to keep it updated

The plugin keeps improving — new checkpoints get added and existing rules get sharpened as the WCAG standard evolves and as we learn from real audits. You only receive those changes when you update, so every so often type these two slash commands at the Claude prompt (the same place you installed it):

/plugin marketplace update eusd-ada-toolkit
/plugin update ada-wcag@eusd-ada-toolkit

Run both, in that order: the first refreshes the marketplace catalog so Claude sees the new version, and the second installs it. This marketplace doesn't auto-refresh, so the update command alone can miss a new release.

What the plugin doesn't cover

The plugin doesn't replace human testing. Still tab through your work, zoom to 200%, run axe DevTools, and test with a screen reader. The plugin and automated checks handle much of the work; the manual workflow below covers the rest.

01

Proper keyboard access

WCAG 2.1.1, 2.1.2 · Level A

What it means

Every interactive thing on the page — buttons, links, form inputs, custom widgets — must be reachable and operable using only the keyboard. Tab moves forward, Shift+Tab moves back, Enter activates links and buttons, Space activates buttons and toggles checkboxes, arrow keys move within widgets like menus or radio groups, and Esc closes modals and popovers.

Users who can't or don't use a mouse — including people with motor disabilities, low vision, and anyone using a screen reader — rely on this completely. A button you can only click with a mouse doesn't exist for them.

See it

Inaccessible

Delete

Try tabbing to it. You can't. A div with an onclick handler is invisible to keyboards.

Accessible

Tab to it, press Enter or Space. It works.

/* Inaccessible — keyboard cannot reach or activate */
<div class="clicky" onclick="deleteIt()">Delete</div>

/* Accessible — keyboard and screen reader work natively */
<button type="button" onclick="deleteIt()">Delete</button>

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Unplug your mouseOr commit to not touching it. Tab through every interactive element on the page from top to bottom.
  • Verify reachEvery button, link, input, menu, and custom widget receives focus when you Tab to it.
  • Verify operationEnter and Space activate buttons. Enter follows links. Arrow keys move inside radio groups, tabs, and menus. Escape closes modals.
  • Verify no trapsYou can always Tab back out of where you Tabbed into.
02

Proper alt text

WCAG 1.1.1 · Level A

What it means

Every <img> tag needs an alt attribute. The value depends on the image's role:

  • Informative images get descriptive alt text that conveys what the image communicates — not what it looks like. "Smiling student receives certificate from principal" beats "person holding paper."
  • Decorative images (purely visual flourishes, dividers, repeated logos) get alt="". The empty string is a signal to screen readers to skip the image entirely. Omitting alt entirely is not the same — screen readers will then read the filename out loud.
  • Functional images (an icon that's the only content of a link or button) get alt text that describes the action: "Search", not "magnifying glass."
  • Complex images (charts, diagrams, infographics) get short alt text plus a longer description nearby in text — because there's too much information for an alt attribute.
  • Images of text should mostly not exist. If unavoidable, the alt text is the exact text shown.
See it 
/* Bad — filename gets read aloud */
<img src="IMG_4521.jpg">

/* Bad — describes appearance, not meaning */
<img src="award.jpg" alt="a person holding paper">

/* Good — informative */
<img src="award.jpg"
     alt="Principal Garcia presenting the Distinguished School plaque to Quantum Academy staff">

/* Good — decorative */
<img src="divider-flourish.svg" alt="">

/* Good — functional icon in a link */
<a href="/search">
  <img src="magnifier.svg" alt="Search">
</a>

/* Good — complex image with companion description */
<figure>
  <img src="enrollment-chart.png"
       alt="Bar chart: EUSD enrollment by grade, 2024–25. Detailed data below.">
  <figcaption>
    Kindergarten: 612 students. Grade 1: 638. Grade 2: 651...
  </figcaption>
</figure>
EUSD shortcut

EUSD publishes a lot of newsletter photos and construction-project drawings, and they need different alt text. Tell Claude which it's describing: photographs get the scene and its meaning ("Students plant a garden bed outside Room 12"), technical drawings get the labeled content ("Site plan: new shade structure between the MPR and the lower field").

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Browser DevToolsInspect any image. Confirm it has an alt attribute. Read the value — does it describe what the image is communicating?
  • axe DevToolsFlags missing alt attributes and some empty-but-shouldn't-be-empty cases.
  • Bookmarklet testUse a "show alt text" browser bookmarklet (or the WAVE extension) to see every image's alt text inline on the page. Decorative images should appear empty, informative ones should describe the content.
  • The screen-reader testTurn on VoiceOver (Cmd+F5) or NVDA. Navigate through the images. The announcement should make sense in the flow.
03

Descriptive link text

WCAG 2.4.4 · Level A

What it means

The text inside a link should tell you where it goes — even when read in isolation, with no surrounding context. Screen reader users often navigate by pulling up a list of all links on a page. If every link says "click here" or "read more," that list is useless.

The rule of thumb: a link's text should be meaningful when read on its own.

See it

Inaccessible

Read our updated wellness policy. Click here.

A link list shows "click here" — destination unknown.

Accessible

Read the updated wellness policy (PDF, 2 pages).

Out of context, the link still tells you what it is.

/* Bad */
Read our updated wellness policy. <a href="/policy.pdf">Click here</a>.

/* Good */
Read the <a href="/policy.pdf">updated wellness policy</a>
(PDF, 2 pages).

/* Also good — when icon-only links need a label */
<a href="/twitter" aria-label="EUSD on Twitter">
  <img src="twitter.svg" alt="">
</a>

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Read every link out of contextIf "click here" or "read more" appears alone, it fails.
  • Screen reader links listIn VoiceOver: VO+U, then navigate to Links. In NVDA: Insert+F7. Read down the list and confirm each link makes sense alone.
  • WAVE extensionFlags "suspicious link text" (click here, more, etc).
04

Not using color alone

WCAG 1.4.1 · Level A

What it means

Color can never be the only way you communicate something. Required form fields shown only in red, error messages indicated only by a red border, a "save" button that's the only green one in the row — these all fail for users with color blindness, low vision, or anyone viewing the page in grayscale or high-contrast mode.

Color is fine as a reinforcement. The rule is that another signal — text, an icon, an underline, a label, a pattern — has to carry the meaning too.

See it

Inaccessible

Required fields are in red.

Name:

If you can't see red, you can't tell which fields are required.

Accessible

Required fields are marked with an asterisk (*) and in red.

Visible asterisk, programmatic required, screen-reader-only "(required)" text.

/* Bad — red is the only signal */
<label>Name</label>
<input style="border-color: red;">

/* Good — visible asterisk + programmatic required + sr-only text */
<label for="name">
  Name <span aria-hidden="true">*</span>
  <span class="sr-only">(required)</span>
</label>
<input id="name" required>

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Grayscale the pageChrome DevTools → Rendering → "Emulate vision deficiencies" → Achromatopsia. If meaning is lost, you're failing.
  • Check the four common offendersRequired-field indicators, form errors, status badges, and chart legends.
  • Run color-blindness simulationSame DevTools menu has protanopia, deuteranopia, tritanopia. Check that no information disappears.
05

Proper color contrast

WCAG 1.4.3, 1.4.11 · Level AA

What it means

WCAG AA sets minimum contrast ratios between foreground and background:

  • 4.5:1 for normal-size text (under 18pt regular, under 14pt bold)
  • 3:1 for large text (18pt+ or 14pt+ bold)
  • 3:1 for UI components and graphical objects — button borders, form input borders, focus indicators, meaningful icons

The common failures: gray placeholder text, light gray secondary text, low-contrast input borders, and disabled states.

See it

Inaccessible — ~2.3:1

This gray-on-near-white text fails AA for normal text (needs 4.5:1).

Accessible — 14:1+

This text uses the page's ink color on the elevated background. Well above 4.5:1.
/* Bad — ~2.3:1 contrast */
.muted { color: #b0b0b0; background: #fafafa; }

/* Good — 14:1+ contrast */
.text { color: #14110f; background: #ffffff; }

Live contrast checker

Paste in any foreground/background pair and see the verdict.

Large text preview
Normal body text, the kind you'd read in a paragraph.
14.0 contrast ratio Normal AA Large AA UI 3:1

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Built-in browser toolChrome/Edge DevTools: inspect any text, the color picker shows the contrast ratio inline with AA/AAA pass markers.
  • The contrast checker aboveFor palette decisions before code exists.
  • axe DevTools / LighthouseBoth catch contrast failures on the rendered page.
  • Don't forget the four statesDefault, hover, focus, disabled. Each can have different colors — each must pass.
06

Tables for data, not layout

WCAG 1.3.1 · Level A

What it means

The <table> element is for tabular data — information with a meaningful relationship between rows and columns. It is not a layout tool. Modern CSS (flexbox, grid) handles layout.

When a table really is the right element, it needs structural markup so screen readers can navigate it: <thead> and <tbody>, header cells (<th>) with scope, and a <caption> describing what the table contains.

</table>

/* Bad — data table with no structure */
<table>
  <tr><td>School</td><td>Grade</td><td>Enrollment</td></tr>

How to check
  • Inspect every <table>Confirm it contains actual rows-and-columns data. If it doesn't, replace it with CSS layout.
  • Look for <caption> and scoped <th>Both must be present on real data tables.
  • Screen reader navigationIn VoiceOver, navigate to the table and press Ctrl+Opt+arrow. Each cell should be announced with its row and column headers.
  • axe DevToolsFlags layout tables and missing headers.
07

Forms properly coded & labeled

WCAG 1.3.1, 3.3.1, 3.3.2, 4.1.2 · Level A

What it means

Forms are where most accessibility audits go wrong. The requirements:

  • Every input has a visible <label> associated to it via for/id. Placeholders are not labels.
  • The type attribute matches the content (email, tel, url, number, date).
  • Required fields use the required attribute and a visible indicator.
  • Errors are identified in text (not just color), tied to the input via aria-describedby, and the input has aria-invalid="true".
  • Related inputs (like radio groups or address blocks) are wrapped in a <fieldset> with a <legend>.
  • Submit buttons have descriptive text — "Submit application", not "Submit".
  • autocomplete attributes are set so browsers and password managers can help users fill faster.
See it

Inaccessible

No label. Placeholder disappears on focus. type="text" instead of email.

Accessible

We'll send your confirmation here. 
/* Bad */
<input type="text" placeholder="Email address">

/* Good — label, correct type, autocomplete, required, help text linked */
<label for="email">
  Email address <span aria-hidden="true">*</span>
  <span class="sr-only">(required)</span>
</label>
<input id="email"
       type="email"
       autocomplete="email"
       required
       aria-describedby="email-help">
<span id="email-help">We'll send your confirmation here.</span>

/* Good — radio group wrapped in fieldset */
<fieldset>
  <legend>Preferred contact method</legend>
  <label><input type="radio" name="contact" value="email"> Email</label>
  <label><input type="radio" name="contact" value="phone"> Phone</label>
</fieldset>

/* Good — error linked to input */
<label for="zip">ZIP code</label>
<input id="zip"
       type="text"
       aria-invalid="true"
       aria-describedby="zip-error">
<span id="zip-error" role="alert">
  Please enter a 5-digit ZIP code.
</span>

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Click every labelClicking a label should focus its input. If it doesn't, the association is broken.
  • Tab through the formEvery input is reachable. Label is read by the screen reader before the input.
  • Submit invalid dataErrors must appear in text, link to the input, and announce to a screen reader.
  • axe DevToolsCatches missing labels, placeholder-as-label, fieldset/legend issues.
08

Proper use of headings

WCAG 1.3.1, 2.4.6 · Level A / AA

What it means

Headings (<h1> through <h6>) are the page's outline. Screen reader users navigate by jumping heading to heading. A page with no headings, or with headings used to fake font sizes, is unnavigable.

The rules:

  • Exactly one <h1> per page, describing the page's main topic.
  • No skipping levels on the way down: don't follow an <h2> with an <h4>.
  • Headings reflect structure, not styling. If you want big bold text that isn't a heading, use CSS, not a heading tag.
  • Heading text is descriptive. "Overview" tells you less than "What we offer families."
See it 
/* Bad — headings used for size; multiple h1s; level skips */
<h1>Welcome</h1>
<h1>About Us</h1>
<h4>Our History</h4>
<div style="font-size:24px;font-weight:bold;">Our Programs</div>

/* Good — single h1, no skipped levels, descriptive */
<h1>Quantum Academy</h1>

  <h2>About our school</h2>
    <h3>School history</h3>
    <h3>Mission and vision</h3>

  <h2>Our programs</h2>
    <h3>STEAM electives</h3>
    <h3>After-school enrichment</h3>

The plugin enforces this as you write code and flags it during an audit.

How to check
  • The headings outline testInstall the HeadingsMap browser extension. The page outline should read like a logical table of contents — not a random scatter.
  • One h1 onlyIn DevTools console: document.querySelectorAll('h1').length. Should be 1.
  • No skipped levelsaxe DevTools and Lighthouse both flag this.
  • Screen reader headings listVoiceOver: VO+U → Headings. Read down — does the structure make sense?
09

Embeds are accessible

WCAG 2.4.1, 4.1.2 · Level A

What it means

Anything embedded from another source — a YouTube video, a Google Map, a third-party form, a social media widget — has two accessibility concerns:

  1. The embed itself. Every <iframe> needs a title attribute that describes what's inside it. Screen readers announce this so users know what they're encountering before they enter it.
  2. The content inside. If you embed a YouTube video, the video itself has to be accessible (captioned — see point 12). If you embed a form, that form needs labels. You can't outsource compliance — if it's on your page, it counts.

Common offenders: Google Maps iframes with no title, YouTube embeds of un-captioned videos, third-party signup forms with poor labeling, Twitter/X embeds with no fallback.

See it 
/* Bad — no title, screen reader announces "iframe" */
<iframe src="https://www.google.com/maps/embed?..."></iframe>

/* Good — descriptive title */
<iframe src="https://www.google.com/maps/embed?..."
        title="Map of Quantum Academy campus, 2245 East Valley Parkway">
</iframe>

/* Good — YouTube embed with title, allowing fullscreen for keyboard */
<iframe src="https://www.youtube.com/embed/VIDEO_ID"
        title="Superintendent's spring 2026 update"
        allowfullscreen>
</iframe>

/* Good — for decorative iframes (rare), title is still required by WCAG */
<iframe src="decorative.html"
        title="Decorative animation"
        aria-hidden="true"
        tabindex="-1">
</iframe>

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Inspect every iframeIn DevTools, search for "iframe". Every one needs a meaningful title.
  • Tab into the embedCan you reach the controls inside (video play button, map zoom, form fields) by keyboard? If not, that embed isn't usable for keyboard-only users.
  • Check what's actually insideA YouTube embed with no captions fails the whole page. Open the video and verify captions exist and are real (not auto-generated).
  • Provide alternatives where neededIf the embed is broken or third-party-non-compliant, link to an accessible alternative on the same page.
10

Zoom to 200% without breaking

WCAG 1.4.4, 1.4.10 · Level AA

What it means

Two related criteria:

  • 1.4.4 Resize text: text can be enlarged to 200% without loss of content or functionality.
  • 1.4.10 Reflow: content reflows to a 320 CSS-pixel-wide viewport without requiring two-dimensional scrolling. In practice: pinch-zoom on mobile, browser zoom on desktop — content should adapt, not get cut off or require side-scrolling.

The common failures: fixed-pixel widths on containers, text in images that doesn't scale, fixed positioning that overlaps content at zoom, and horizontal layouts that don't collapse to a single column at small widths.

See it

This page is the demo. Press Ctrl++ (or Cmd++) repeatedly until you're at 200%. Then 300%. Then 400%. Content reflows; nothing gets cut off; there's no horizontal scrollbar.

Why this works

Everything sizes in rem, em, percentages, or clamp(). Containers use max-width, not fixed width. Multi-column grids use grid-template-columns: repeat(auto-fit, minmax(...)) so they collapse when there's no room. Media queries handle the rest.

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Browser zoom testPress Ctrl++ until at 200%. Then 400%. No horizontal scrollbar, no clipped content, no unreachable controls.
  • 320px viewport testChrome DevTools → Device toolbar → set to 320 × 568. Page should render and function without horizontal scrolling.
  • Text-only zoomIn Firefox: View → Zoom → Zoom Text Only. Test at 200%. Catches images-of-text and fixed pixel font sizes.
11

Linked files are ADA compliant

WCAG (full standard applies to the linked document)

What it means

If your page links to a PDF, a Word doc, a PowerPoint, or any other downloadable file, that file has to meet the same accessibility standard as the page itself. Linking to an inaccessible PDF doesn't put it out of scope — it puts you out of compliance.

For each document type, the baseline requirements:

  • PDFs: tagged structure, real text (not scanned images), document language set, reading order verified, alt text on images, document title set in metadata, no contrast or color-only failures.
  • Word docs: heading styles used for structure (not bold-and-bigger text), alt text on images, table headers marked, descriptive hyperlink text, document language set.
  • PowerPoint: every slide has a unique title (use slide layouts), alt text on images, reading order verified per slide, contrast checked, no important info in speaker notes only.
  • Spreadsheets: column headers, named ranges for important regions, alt text on charts and images, no critical info conveyed by cell color alone.
Tooling

These are the checks the web developer runs — most work from inside the app that produced the file:

  • Word, PowerPoint, Excel: Review → Check Accessibility. Built-in.
  • Adobe Acrobat Pro: Tools → Accessibility → Accessibility Check. Generates a report.
  • For PDFs you didn't create: open in Acrobat Pro and run the check. If it fails, the source document needs to be remediated, or replaced with a tagged version.
EUSD reality check

The single biggest source of accessibility findings for K-12 districts is linked PDFs — board agendas, policies, flyers, forms. Build a habit: every time you link a document, send the file to the web developer to check before publishing the link.

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Inventory the linksFor any page you're publishing, list every link to a file. Send each one to the web developer to confirm it passes before you publish.
  • Tell users the format"(PDF, 2 pages)" or "(Word doc)" in or after the link.
  • Read the PDF with a screen readerOpen in Acrobat or browser. Use VoiceOver/NVDA to read it. Does the reading order make sense? Are images described? Is there real text?
12

Videos properly captioned

WCAG 1.2.2, 1.2.3, 1.2.5 · Level A / AA

What it means

Every video with audio content needs accurate, human-edited captions. YouTube's auto-generated captions are not sufficient — they're explicitly treated as failing for ADA compliance. Auto-captions misspell names, mishear domain-specific words, and miss speaker changes.

Requirements:

  • Captions for all pre-recorded video with audio (1.2.2, Level A). Must be accurate, properly timed, and identify speakers when not visible.
  • Audio description for content shown visually that isn't conveyed in the audio (1.2.5, Level AA). For most school videos this means: don't have important content appear only on screen — say it out loud too.
  • Transcripts for audio-only content like podcasts (1.2.1, Level A).
  • Live video with audio needs real-time captions if it's broadcast (1.2.4, Level AA) — this applies to board meeting livestreams.
In practice
  • YouTube: upload your own SRT file. Or use YouTube's auto-captions as a starting point and edit them in YouTube Studio. Never publish with raw auto-captions.
  • Vimeo: same — upload your own caption file.
  • Self-hosted: use the <track> element with a WebVTT file.
  • For Thrillshare-hosted video: confirm captions exist on the underlying YouTube/Vimeo source, since Thrillshare embeds it.
/* Self-hosted video with captions */
<video controls>
  <source src="welcome.mp4" type="video/mp4">
  <track kind="captions"
         src="welcome-en.vtt"
         srclang="en"
         label="English"
         default>
  <track kind="captions"
         src="welcome-es.vtt"
         srclang="es"
         label="Spanish">
</video>

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Turn captions onPlay the video. Turn on CC. Read along for a minute. Are speakers identified? Are technical terms and names spelled right? Auto-captions almost always fail this.
  • YouTube Studio checkFor YouTube videos, open the video in Studio → Subtitles. Confirm a manually-edited or uploaded caption track exists, not just "auto-generated."
  • Confirm syncCaptions must be timed to the audio, not lagging or running ahead.
  • For live broadcastsVerify live captioning is configured before the event starts, not after.
13

Reading order

WCAG 1.3.2, 2.4.3 · Level A

What it means

The order content appears in the HTML source determines what screen readers announce, and what keyboard users Tab through. That order must match the visual reading order — top to bottom, left to right (or right to left for RTL languages).

Problems happen when CSS rearranges content visually without changing the source order. Flexbox order, CSS Grid grid-area, and negative margins can all produce a layout where what looks first on screen is last in the source — or vice versa.

See it

Bad — visual ≠ source order

Visual: 1 → 2 → 3 → 4. Source: 3 → 1 → 4 → 2.

3. Source position 3 (shown first visually)
1. Source position 1 (shown second)
4. Source position 4 (shown third)
2. Source position 2 (shown last)

A screen reader reads "3, 1, 4, 2." Nothing makes sense.

Good — visual = source order

Visual: 1 → 2 → 3 → 4. Source: 1 → 2 → 3 → 4.

1. First in source, first visually
2. Second in source, second visually
3. Third in source, third visually
4. Fourth in source, fourth visually

Reading order, Tab order, and visual order all agree.

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Disable CSSFirefox: View → Page Style → No Style. Chrome: use the Web Developer extension. The unstyled page should still read top-to-bottom in a logical order.
  • Tab throughTab order must match visual order. If focus jumps around the page unexpectedly, your source order is off.
  • Screen reader read-throughUse VO+A in VoiceOver or NVDA's say-all (Insert+↓) to read the whole page. Listen for content that arrives out of place.
14

Skip links

WCAG 2.4.1 · Level A

What it means

A "skip to main content" link is the first focusable element on every page. It lets keyboard users — who would otherwise have to Tab through the entire site header and navigation on every single page — jump straight to the content.

It's typically visually hidden until it receives focus, at which point it appears (this page has one — press Tab from the URL bar and it shows up at top left).

Requirements: it must be the first focusable element, it must be visible when focused, and it must work — clicking it (or pressing Enter on it) moves focus to the main content area.

See it

This page has a working skip link. Try it: reload the page, then press Tab once. The link appears at the top of the page. Press Enter — focus moves past the masthead to the main content.

/* HTML — first focusable element on the page */
<body>
  <a href="#main" class="skip-link">Skip to main content</a>

  <header>...site nav...</header>

  <main id="main">
    ...page content...
  </main>
</body>

/* CSS — visually hidden until focused */
.skip-link {
  position: absolute;
  top: 0;
  left: 0;
  background: #000;
  color: #fff;
  padding: 12px 18px;
  font-weight: 600;
  text-decoration: none;
  transform: translateY(-110%);
  transition: transform 0.15s ease;
  z-index: 1000;
}
.skip-link:focus {
  transform: translateY(0);
}

The plugin enforces this as you write code and flags it during an audit.

How to check
  • The Tab testReload the page. Press Tab exactly once. The skip link should appear visibly.
  • The Enter testWith the skip link focused, press Enter. Focus must move into the main content area. The next Tab press should land inside <main>, not back in the header.
  • Don't use display:noneIf the skip link is hidden with display:none or visibility:hidden, it won't appear in the tab order at all. Use transform, top, or clip.
15

Focus indicator

WCAG 2.4.7 · Level AA

What it means

When a user Tabs to an interactive element, there must be a visible indication of where focus is. By default, browsers show a focus ring (typically a blue outline). Designers often dislike how this looks and ask developers to remove it with outline: none. Doing this without providing an alternative is one of the most common accessibility failures on the web.

Requirements:

  • Every focusable element shows a visible focus indicator when focused via keyboard.
  • The indicator has at least 3:1 contrast against the surrounding background (WCAG 2.4.11, also AA).
  • The indicator should not be ambiguous — a 1px border change is often not enough.
  • Use :focus-visible rather than :focus to avoid showing the ring when users click with a mouse, where it's unnecessary visual noise.
See it

Tab around this page right now. Every link, button, tab, input, and accordion shows a clear blue ring when it receives focus. That's a custom focus indicator — high contrast, thick enough to see, offset from the element for clarity.

/* Bad — removes focus indicator entirely */
button:focus { outline: none; }

/* Bad — too subtle, fails contrast */
button:focus { outline: 1px dotted #ccc; }

/* Good — custom, high-contrast, only shows for keyboard users */
:focus { outline: none; }
:focus-visible {
  outline: 3px solid #1d4ed8;
  outline-offset: 2px;
  border-radius: 4px;
}

The plugin enforces this as you write code and flags it during an audit.

How to check
  • Tab through everythingSlowly. At every focus stop, you should clearly see which element is focused without having to look hard.
  • Search the CSS for "outline: none" or "outline: 0"Every instance needs a corresponding focus replacement nearby.
  • Check contrast of the focus ring3:1 against background. Use the contrast checker in point 5.
  • Test on custom widgets tooTabs, accordions, custom selects, sortable table headers. Devs often style their focus rings on inputs and buttons but forget custom components.
Free tooling

axe DevTools — a free accessibility scanner

axe DevTools is a free browser extension from Deque Systems. It scans the page you're viewing and reports accessibility problems — missing labels, contrast failures, ARIA misuse, heading-order skips, and more. It's the industry-standard automated checker, and it's what "run axe DevTools" means everywhere in this training. Automated tools catch roughly 30–40% of issues on their own, so axe is a fast first pass — not the whole job.

How to install it

  1. Open the Chrome Web Store (or Firefox Add-ons / Edge Add-ons).
  2. Search for axe DevTools — the publisher is Deque Systems.
  3. Click Add to Chrome → Add extension. The free tier is all you need for this.

How to run a scan

  1. Open the page you want to check in the browser.
  2. Open DevTools: press F12, or right-click the page and choose Inspect (Mac: Option+Command+I).
  3. Click the axe DevTools tab along the top of the DevTools panel.
  4. Click Scan all of my page.
  5. Review the results grouped by severity (Critical, Serious, Moderate, Minor). Click any issue to highlight the element on the page and read the explanation and suggested fix.

Fix what axe finds, then take the same page through the manual checks below — axe can't tell you whether the tab order makes sense or whether a caption is human-edited.

Other DevTools checks worth knowing

  • Emulate vision deficienciesOpen the Command Menu (Ctrl/Cmd+Shift+P), type "Rendering", choose Show Rendering, then scroll to Emulate vision deficiencies and pick protanopia, deuteranopia, or blurred vision. Confirms you're not relying on color alone (checkpoint 4).
  • Inspect contrast on any elementRight-click text → Inspect, then in the Styles pane click the small color swatch next to a color value. The picker shows the contrast ratio and whether it passes AA.
  • Read an element's name & roleIn the Elements tab, open the Accessibility pane to see the computed name, role, and state of whatever you've selected — the same information a screen reader gets.
Free tooling

Lighthouse — a quick accessibility score

Lighthouse is built into Chrome and Edge — nothing to install. It runs a batch of automated audits and gives the page a 0–100 Accessibility score, alongside Performance, Best Practices, and SEO. Under the hood its accessibility audits use the same axe-core engine as axe DevTools, so the two rarely disagree — think of Lighthouse as the quick numeric snapshot and axe DevTools as the detailed issue list.

How to run it

  1. Open the page in Chrome or Edge.
  2. Open DevTools (F12) and click the Lighthouse tab.
  3. Under Categories, tick Accessibility (untick the others for a faster, focused run).
  4. Pick a device — Mobile or Desktop.
  5. Click Analyze page load and wait a few seconds for the report.

How to read the score

  • The number is a starting point, not a verdictThe score is weighted, and a 100 does not mean the page is accessible — it only means the automated checks passed. Lighthouse says as much itself.
  • Work the failing auditsExpand each failed item to see the affected elements and a "Learn more" link with the fix. That list is more useful than the number.
  • Don't skip "Additional items to manually check"Lighthouse lists checks it can't automate — focus order, meaningful alt text, logical reading order. Those are yours (or the screen-reader pass) to confirm.
  • It only sees the loaded stateIt audits the page as it loads; content behind a modal, menu, or interaction won't be tested. Re-run with that content open, or rely on the manual workflow.
axe vs. Lighthouse

Same engine, different jobs. Use Lighthouse for a fast score you can track over time (and a free Performance/SEO read while you're there). Use axe DevTools when you want the cleanest, most actionable list of issues to fix. Neither lifts the ~30–40% ceiling on what automation can find.

Division of labor

What tools catch — and what only a human can

Three things work on accessibility, in layers. Each catches more than the one before it, but none of them replaces the layer above. Knowing where each one stops is how you avoid a false sense of "it passed."

Automated checkers (axe, Lighthouse)

Fast and mechanical — they run in seconds and catch what can be measured from the rendered page, roughly 30–40% of issues.

  • They catchMissing alt attributes, missing form labels, text-contrast failures, invalid or misused ARIA, missing lang or page title, heading-level skips, duplicate IDs.
  • They can't judge meaningWhether alt text is accurate, whether link text makes sense out of context, whether the reading or tab order is logical. A wrong-but-present alt passes just like a correct one.
  • They can't test interactionWhether a custom widget actually works by keyboard, whether focus is visible in use, whether a caption is human-edited rather than auto-generated.

The ada-wcag skill

It reads and writes the source, so it sees patterns a checker can't — and applies the full WCAG 2.2 AA ruleset as it builds, then again in a guided audit.

  • It catchesEverything a checker does, plus code-level issues only visible in the source: target sizes, drag-only interactions, focus hidden behind sticky headers, inconsistent labels, missing skip links, color used as the only signal — and it builds these right from the start instead of flagging them after.
  • It flags, it doesn't guessWhere correctness depends on intent or content it can't see, it marks the item "verify manually" rather than passing it silently.
  • Where it stopsRuntime behavior (real focus order and screen-reader output in a browser), contrast that depends on runtime theming, the quality of alt text and captions, linked PDFs and Office files, and cross-page consistency when only one file is open.

You — the human

The only layer that can confirm a page actually works for a real person. Nothing ships on tools alone.

  • Tab through itNo mouse. Confirm every control is reachable, focus is visible, and keys do what they should.
  • Listen to itRun VoiceOver or NVDA on the key flows. Does the reading order make sense? Are images and controls announced usefully?
  • Judge the meaningIs the alt text right, the link text clear, the caption accurate, the color not the only cue? Tools can't make these calls — you can.
  • Handle linked documentsSend PDFs and Office files to the web developer to check — automated page scans never see inside them.
  • Sign offMake the final compliance judgment. The tools get you most of the way; this is the rest.
The short version

Checkers find the mechanical failures. The skill prevents most of them at build time and flags the rest. Only a human can confirm the page is actually usable. Use all three — and never let a green checkmark stand in for tabbing through the page yourself.

The bigger workflow

Testing every page before it ships

The ada-wcag plugin will get you most of the way there. Use this workflow to verify the rest.

  • Run axe DevTools or LighthouseCatches contrast, missing alt text, ARIA misuse, missing labels, heading-level skips. Roughly 30–40% of issues.
  • Tab through the whole pageNo mouse. Verify every interactive element is reachable, has visible focus, and responds to expected keys.
  • Zoom to 200%And then 400%. Reflow, no horizontal scroll, no clipped controls.
  • Simulate color-blindness and grayscaleChrome DevTools → Rendering → "Emulate vision deficiencies." Confirms point 4.
  • Run a screen reader on the key flowsVoiceOver (Cmd+F5) or NVDA. Walk through the page reading-order; navigate the headings list; navigate the links list; submit the form.
  • Run the accessibility auditType "run accessibility audit" and Claude walks you through every issue by severity, one fix at a time. Fix anything flagged, then re-audit.
  • For each linked fileSend the file to the web developer to check — don't assume a PDF or Office doc is compliant.
  • For each videoConfirm captions are human-edited and synced.
