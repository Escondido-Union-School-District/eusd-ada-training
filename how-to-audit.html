Hands-on walkthrough

Run an accessibility audit, start to finish

A step-by-step walkthrough of the ada-wcag plugin auditing a real page. You point Claude at an example registration page that was built with deliberate accessibility problems, type one command, and watch it find every issue and fix them one at a time. Follow along on your own machine.

Back to the 15 checkpoints
Before you start

What you need

  • Claude Code installed and working in a terminal.
  • The ada-wcag plugin installed. If you have not done that yet, the two install commands are on the main training page. It takes about a minute.
  • The example page. Download spring-family-night-inaccessible.html and save it to a folder of its own (for example a new audit-demo folder).
The example page

A page built to fail

The example is a fictional Spring Family Night registration page for "Lincoln Elementary." It looks finished: a hero banner, an event schedule, a highlights video, and a sign-up form. Underneath the nice styling, it was seeded with the kinds of accessibility problems that show up on real district pages.

Intentionally broken

This page is a practice target. It is not a real EUSD page and is not a model to copy. Every accessibility problem in it is there on purpose so the plugin has something to find. Do not reuse its code.

A few of the problems hiding in it: form fields with no labels, a "button" that a keyboard cannot reach, a video with no captions, text that disappears when you zoom in, and a required field marked only by a red border. You do not need to find these yourself. That is the plugin's job.

The walkthrough

Auditing the page, step by step

  1. Open the folder in Claude Code

    In your terminal, change into the folder where you saved the example page, then start Claude Code there.

    Terminal Your regular command line.
    $cd audit-demo $claude

  2. Ask for an audit

    At the Claude prompt, type the audit request in plain language. The plugin recognizes this and switches into audit mode.

    Claude Code Type this at the Claude prompt, not your terminal.
    >run accessibility audit

  3. Watch it scan the page

    Claude finds the HTML and its styles, then checks the page against the full WCAG 2.2 AA criteria list. It reads the source the way a screen reader and a keyboard would, not just how the page looks. After a few seconds it reports back.

    Claude Code What Claude prints back.
    # Found 1 HTML file: spring-family-night-inaccessible.html # Styles: inline <style> block resolved Auditing against WCAG 2.2 AA...

  4. Read the findings, grouped by severity

    The results come back sorted Critical first, then Serious, then Moderate, so you fix the things that block people before the things that just cause friction. Here is the real result for this page.

    Audit results: 17 issues

    5 critical · 6 serious · 6 moderate

    Critical blocks access, fix first
    • 1.3.1 / 3.3.2 / 4.1.2Form fields have no labels. All four registration inputs rely on placeholder text only, so a screen reader announces an empty field.
    • 2.1.1 / 4.1.2"Register Now" is a div, not a button. A keyboard cannot reach it or activate it, so keyboard and screen reader users cannot submit.
    • 1.2.2 / 1.2.3The video has no captions or transcript. Deaf and hard-of-hearing visitors get nothing from it.
    • 2.4.1No skip link. Keyboard users must tab through the whole header before reaching the content.
    • 1.4.1 / 3.3.2Required field shown by color only. The email field is marked required with just a red border, invisible to many users.
    Serious significant barrier
    • 2.4.7Focus indicator removed everywhere. *:focus { outline: none } with no replacement, so keyboard users lose track of where they are.
    • 1.4.3Low-contrast intro text. Gray #999 on white is about 2.8 to 1, below the 4.5 to 1 minimum.
    • 1.4.3Placeholder text used as labels. At #c0c0c0 it is about 1.8 to 1, and it vanishes once typing starts.
    • 1.4.11Input borders too faint. About 1.6 to 1 against white, below the 3 to 1 minimum for controls.
    • 1.4.4 / 1.4.10Content clips when zoomed. A fixed-height hero with hidden overflow cuts off the date and time at 200 percent zoom, and fonts are set in fixed pixels.
    • 1.3.5No autocomplete on personal fields. Name, email, and phone lack autocomplete, so browsers and password managers cannot help.
    Moderate friction, fix after the rest
    • 2.4.4"Click here" link text. The calendar link reads "Click here," meaningless out of context, and repeats itself.
    • 1.3.1 / 2.4.6Heading levels skip. The page jumps from h1 to h4 and places an h3 out of order.
    • 1.3.1Schedule built from divs. The time-and-activity grid is styled divs, not a real table, so it is not navigable as data.
    • 1.3.2Reading order does not match the view. CSS order shows the urgent notice first visually but it comes last in the source.
    • 1.1.1Decorative divider has alt text. A spacer image carries alt="horizontal line" and should be empty.
    • 2.4.4PDF link lacks detail. The handbook link gives no file type or size, and the document needs its own accessibility check.

  5. Fix issues one at a time

    Type fix and the plugin walks through the issues in order. For each one it shows the problem, who it affects, and the exact change it proposes, then waits. Nothing is edited until you approve it. Here is the first issue.

    Claude Code The fix prompt for one issue.
    >fix   PROBLEM (2.1.1 / 4.1.2, Critical) "Register Now" is a <div> with an onclick handler. A keyboard user cannot focus it or press it, so they cannot submit the form.   FIX Replace the div with a real <button type="submit">, which is keyboard operable and announced as a button by screen readers.   [y] Apply fix  [s] Skip  [q] Quit >y Applied. Marked fixed. Next issue...

    Press y to apply, s to skip, or q to stop. Work down the list until the critical and serious issues are gone. You can stop any time and pick up later.

  6. Track progress and re-audit

    The plugin saves its progress to a .wcag-progress.json file in the folder, so a long audit can span more than one sitting. When you come back, it tells you what is fixed and what remains. After you finish a pass, run the audit again to confirm the count has dropped and nothing new slipped in.

Try it on the broken page only

If you are practicing, apply the fixes to your downloaded copy, not to a real page yet. The point of this example is to see the full find-and-fix loop on a page where you already know the answers.

Two more ways to use it

The plugin does more than full audits

A full audit is one of three ways the same plugin works. The other two fit smaller moments in a normal workflow.

  • Quick Check a single piece

    When you only want to review one part of a page, ask about that part. The plugin checks just that piece and reports inline, with no full audit and no progress file.

    >check the registration form on this page for accessibility

  • Build it right from the start

    When Claude writes new web code with the plugin installed, it applies the same rules as it builds, so labels, contrast, focus styles, and semantic structure are correct in the first draft instead of being fixed later.

    >build an RSVP form for our open house
